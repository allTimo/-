# Центр управления агентами — локальный дашборд

Локальный сайт, который показывает сеть агентов-маркетолога и её работу: кто из агентов
включён, какие задачи в работе, какие проекты (ЖК) они ведут, сколько токенов и рублей
израсходовано и как подключить нового агента.

Данные берутся **только** из вашей машины: логи сессий DSH, проекция сессий и папка
`marketing-agents/registry`. Ничего не отправляется наружу.

---

## Как открывать

**Основной способ — один: ярлык «Панель управления» на Рабочем столе.**
Двойной щелчок поднимает панель (через задачу планировщика Windows, а не как
дочерний процесс DSH) и открывает браузер. Терминал не нужен.

Тот же самый запуск одной командой (она же делает автопроверку):

~~~powershell
powershell -ExecutionPolicy Bypass -File marketing-agents\install\check-dashboard.ps1
~~~

Скрипт **сам проверяет панель перед открытием** — это ответ на требование
«проверяй всегда на баги перед запуском»:

1. если порт 8787 не слушается — поднимает панель задачей планировщика и ждёт до 20 с;
2. `GET /` → 200;
3. `GET /api/state` → 200 и **валидный JSON**;
4. headless-проверка страницы: все 9 вкладок на месте, нет «Не удалось загрузить»,
   интерфейс отрисовался, в консоли браузера нет ошибок JS
   (штатные предупреждения Chromium про extensions/GPU ошибками **не считаются**);
5. печатает одну строку — `Панель работает: http://127.0.0.1:8787 (вкладок 9, ...)`
   или `ПАНЕЛЬ НЕ РАБОТАЕТ: <причина>` — и возвращает код 0 или 1.

### Почему панель больше не «падает»

Раньше сервер запускался дочерним процессом сессии и умирал вместе с DeepSeek
Harness — отсюда `ERR_CONNECTION_REFUSED`. Теперь панель поднимает **задача
планировщика Windows «DSH Dashboard»**, которая к DSH не привязана: перезапуск
приложения её не затрагивает. Управление задачей:

~~~powershell
powershell -ExecutionPolicy Bypass -File marketing-agents\install\dashboard-task.ps1 -Status
powershell -ExecutionPolicy Bypass -File marketing-agents\install\dashboard-task.ps1 -Run
~~~

- `-Install` создаёт задачу и ярлык; `-Remove` удаляет; `-Status` показывает состояние;
- задача создаётся **без триггера** — только запуск по требованию. Триггер входа в
  систему добавляется отдельно и только по явной просьбе: `-Logon on` (с паузой 20 с),
  `-Logon off` — убрать. По умолчанию в автозапуск ничего не попадает.

### Если панель всё-таки не отвечает

~~~powershell
# что происходит: задача, ярлык, порт
powershell -ExecutionPolicy Bypass -File marketing-agents\install\dashboard-task.ps1 -Status

# журналы сервера
marketing-agents\dashboard\logs\server.out.log
marketing-agents\dashboard\logs\server.err.log
~~~

### Только для разработки

Запуск сервера напрямую, без задачи и без проверок:

~~~powershell
node marketing-agents/dashboard/serve.mjs
~~~

Этот способ не переживает перезапуск DSH — для повседневной работы пользуйтесь
ярлыком или `check-dashboard.ps1`.

### Обновить данные

Кнопка **«Обновить данные»** в правом верхнем углу панели — или:

~~~powershell
node marketing-agents/dashboard/collector/collect.mjs
~~~

## Блок «Отчёт Агента 1 по конкурентам» (первым в «Аналитике»)

Первый блок раздела: сводка по конкурентам, таблица по каждому проекту, цены по типам квартир,
динамика, риск-флаги и источники. Данные — **профили конкурентов от движка**:
`01-competitor-watch/data/clients/<client-id>/competitor-profiles/*.json` + `_summary.json`.

### Схема профиля (для движка и для тех, кто читает)

```json
{
  "project": "ЖК СОУЛ", "source_url": "…", "source_platform": "cian",
  "collected_at": "2026-11-01", "distance_km": 5.01, "class": "бизнес",
  "metrics": {
    "lots_in_sale":  { "value": 28, "unit": "лотов", "source": "cian (…)", "collected_at": null,
                       "method": "http", "accuracy": "высокая", "comment": "лоты на публичной странице проекта" }
  },
  "derived": { "sales_speed_per_week": { "value": null, "method": "estimate",
                "comment": "нужно минимум 2 недели наблюдений (накоплено 1)" } },
  "by_rooms": { "студии": { "count": 3, "median_price_per_m2": 664362 }, "1": { … }, "2": { … }, "3": { … }, "4+": { … } },
  "risk_flags": [ { "code": "no_history", "level": "info", "comment": "…" } ],
  "limitations": [], "history": { "weeks": 1, "needed": 2, "available": false }
}
```

Сводка `_summary.json`: `client`, `generated_at`, `projects`, `lots_total`,
`price_per_m2_median`, `risk_flags[]`, `rosreestr{status, detail, attempts, checked_at}`, `files[]`.

### Группы блока (расширение от 01.11.2026)

| Группа | Что показывает | Источник |
|---|---|---|
| Сводка | конкурентов, лотов, медиана ₽/м², акции, риск-флаги, метрик со значением | `_summary.json` + профили |
| Таблица конкурентов | лоты, медианы и мин. вход ₽, медиана цены, средняя площадь, акции площадки, бронь, динамика | Циан/Авито (http) |
| **Корпуса и стройка** | корпусов названо, сроки ввода, готовность %, шахматка сайта (всего/в продаже/продано/бронь), **доля проданного по сайту застройщика** | сайт застройщика, метод `dom` |
| **Акции и программы** | тексты акций с сайта («СКИДКА ДО 8%», «РАССРОЧКА …»), число ипотечных программ | сайт застройщика, `dom` |
| **Официальные данные: Росреестр / ЕИСЖС** | статус источника, корпуса/квартиры/ДДУ — «данных нет: причина» | ЕИСЖС, Росреестр (сейчас недоступны) |
| Цены по типам квартир | студии / 1 / 2 / 3 / 4+ | лоты площадок |
| Динамика | скорость продаж, absorption, месяцы до распродажи, динамика цены входа и предложения | расчёт, `estimate` |
| Риск-флаги | резкий рост предложения, сброс цен, агрессивные акции | профили |

**Доля проданного по сайту застройщика** считается панелью ТОЛЬКО когда есть оба числа
(всего квартир и продано по шахматке). Подписана «**НЕ Росреестр**» — это данные сайта, а не ДДУ.

### Три режима блока (по конкурентам / по метрикам / по источникам)

Режим — это свойство ВСЕГО блока, а не отдельной группы. Каждый режим даёт **структурно другое содержимое**:

| Режим | Структура | Первый столбец |
|---|---|---|
| По конкурентам | строка = конкурент, столбцы = метрики (аккордеон групп) | «Проект» |
| По метрикам | строка = метрика, столбцы = конкуренты (аккордеона нет по смыслу таблиц) | «Метрика» |
| По источникам | группировка по ИСТОЧНИКУ: что оттуда берём, сколько метрик, проектов, доступность, метод и дата | «Источник» |

**Сохранение состояния:** режим пишется в адрес как `#analytics/<режим>` и дублируется в
`localStorage` (`dsh.cr.mode`). Поэтому работают **назад/вперёд**, ссылка на конкретный режим и
восстановление режима после перезагрузки.

**Автотест поведения** (без него элемент не принимается): `check-dashboard.ps1` открывает
`#analytics/competitors` и `#analytics/metrics`, извлекает текст раздела и **требует, чтобы он
отличался**, а в режиме «по метрикам» был столбец «Метрика». Бейдж-подсветка без смены содержимого =
проверка падает. Именно этого теста не хватало, когда переключатели «подсвечивались, но не меняли».

### Группа «Маркетинг»: бюджеты SpyWords / Keys.so

Группа больше не «заглушка»: у неё свой вид (`kind: marketing`) и **7 метрик** бюджета.

| Метрика (внутренняя) | Сырой ключ движка | Что это |
|---|---|---|
| `marketingBudgetEstimateRub` | `marketing_budget_estimate_rub` | ориентировочный бюджет за период, ₽ |
| `marketingPeriod` | `marketing_period` | за какой период оценка |
| `marketingAds` | `marketing_ads_count` | объявлений |
| `marketingKeywords` | `marketing_keywords_count` | ключевых слов |
| `marketingLandings` | `marketing_landings_count` | уникальных посадочных |
| `marketingSource` | `marketing_source` | `Keys.so` или `SpyWords` |
| `marketingMethod` | `marketing_method` | способ сбора: `api` \| `csv` \| `mcp` |

**Честность (обязательно):** рядом с бюджетом стоит бейдж **«оценка»**, а в группе — подпись
«Ориентировочный бюджет по данным SpyWords / Keys.so — **ОЦЕНКА СЕРВИСА, не фактический расход**».
Это не отчётность застройщика и не наши измерения: сервис оценивает бюджет по объёму рекламы.

**Три состояния, никаких нулей:**

| Состояние | Что видно |
|---|---|
| ключ не подключён (`no_key`) | «Ключ API не подключён: бюджет появится после подключения SpyWords/Keys.so» + таблица со всеми колонками, где в каждой ячейке «данных нет: причина» |
| домена нет в базе (`no_domain`) | «нет данных по домену в базе сервиса» |
| данные есть (`ok`) | таблица с бюджетом, периодом, объявлениями, словами, посадочными, источником, методом, датой и точностью |

### Сопоставление среза с профилем (контракт ключей)

Запись среза и профиль связываются по трём полям, в порядке приоритета:

| Поле записи среза | Что это | Пример |
|---|---|---|
| `project` | **канонический ключ проекта** (совпадает с именем файла профиля) | `zhk-seliger-siti` |
| `name` | человеческое название | `ЖК Селигер Сити` |
| `domain` | домен проекта | `seliger-city.ru` |

Порядок поиска совпадения в панели: **ключ проекта → имя → домен профиля → карта доменов →
нестрогое совпадение по слагу**. Нестрогое совпадение помечается как `ok_fuzzy`: цифры показываем,
но просим уточнить домен.

### Карта доменов: `agent1.competitor_domains`

Если срез отдаёт только домен, а профиль называется по ключу, помогает карта
«домен → канонический ключ проекта» в тонких настройках Агента 1:

```yaml
agent1:
  competitor_domains:
    seliger-city.ru: zhk-seliger-siti
```

Её читают **и движок, и панель**. Редактируется в карточке Агента 1, блок «Тонкие настройки» →
«Домены конкурентов»: можно изменить существующую пару или добавить новую (запись атомарная, с копией).

### Три состояния без данных (не путать)

| Состояние | Когда | Что показано |
|---|---|---|
| `no_key` | ключа API нет | «Ключ API не подключён: бюджет появится после подключения SpyWords/Keys.so» |
| `no_domain` | срез есть, но по проекту данных нет | «нет данных по домену в базе сервиса» |
| `unmatched` | **данные есть, но проект не сопоставлен** | «данные в сервисе есть, но проект не сопоставлен: добавьте домен в карточку конкурента (в срезе: …)» |

Нули вместо отсутствия не показываем ни в одном состоянии.

### Недельные срезы бюджетов (для движка, task-67)

Панель читает `01-competitor-watch/data/clients/<client-id>/budgets/<дата>.json`:

```json
{ "source": "Keys.so", "method": "api", "status": "ok",
  "projects": [ { "project": "ЖК СОУЛ", "budget_estimate_rub": 1250000, "period": "2026-10",
                  "ads_count": 42, "keywords_count": 310, "landings_count": 7,
                  "collected_at": "2026-11-01", "accuracy": "средняя" } ] }
```

Если ключа нет — достаточно `{ "status": "no_key", "note": "…" }`. Если домена нет в базе —
`"status": "no_domain"` в записи проекта. Панель показывает недельную динамику бюджетов
(мини-столбики) с той же пометкой «оценка».

### ПРАВИЛО ПОЛНОТЫ (чтобы метрики не терялись молча)

**Проверять ПОСЛЕ пересборки.** Правило команды: прежде чем сказать «всё сошлось», прогонять
`verify-data.mjs` на свежей выгрузке движка — новый прогон меняет состав ключей, и проверка полноты
обязана это поймать. Именно так и вышло дважды: ключ `reserved_lots` появился после очередного прогона,
и правило полноты честно показало `reservedLots` как неразложенный — это была ошибка панели, а не движка.

Раньше новые поля движка просто не отображались, и этого никто не замечал — так вышло с корпусами.
Теперь в `collector/lib/competitor-report.mjs` есть:

- `METRIC_MAP` / `DERIVED_MAP` — соответствие имён движка нашим;
- `DISPLAY_GROUPS` — **какие ключи в каких группах показываются**;
- `HIDDEN_METRICS` — **явный список скрытых** с причиной (сейчас пуст: показываем всё, что присылает движок).

Правило: **каждая метрика профиля либо в группе отображения, либо в списке скрытых.**
`verify-data.mjs` считает это и падает с перечислением неразложенных ключей. Сейчас:
увидено **35**, разложено **35**, не разложено **0**.

### Правила честности, которые соблюдает блок

| Правило | Как выполнено |
|---|---|
| У каждой метрики — источник и дата | метрика несёт `source`, `collected_at`, `method`, `accuracy`; всё это в подсказке при наведении |
| Нет данных — «данных нет: причина» | берём `comment` движка как причину, нулей не подставляем |
| Оценки помечены | `method: "estimate"` → к значению добавляется «(оценка)» |
| Росреестр/ЕИСЖС не подменяем | статус из `_summary.json.rosreestr` показываем как есть; своими цифрами не закрываем |
| **Ноль там, где признака нет** | если движок прислал `value: 0` с комментарием вида «признака брони нет», коллектор превращает это в «данных нет» (`zeroWasAbsence: true`), а исходный 0 сохраняет в `rawValue` |

**Свежесть:** как в «Тонких настройках» — при открытии раздела сравнивается mtime профилей
со временем сборки, при отставании панель сама пересобирает данные; сверху кнопка «Обновить данные».
`verify-data.mjs` проверяет, что данные не старше профилей.

### Проверки блока в verify-data

Сумма лотов по конкурентам = сводке и `lots_total` движка · число конкурентов совпадает ·
акции сходятся · **у каждой метрики со значением есть источник** · нет метрик без источника ·
**нет нулей вместо «данных нет»** · оценки помечены · источники из ожидаемых ·
Росреестр не подменён.

## Раздел «Аналитика»: графики, срезы, метрики

**Шесть графиков** (свои, на SVG — внешних библиотек нет), переключатель **день / неделя / месяц**
и **фильтр периода 7 / 30 / 90 дней / всё время / произвольный диапазон** (применяется сразу
и к графикам, и к блоку «за период»):

1. динамика во времени — доход · себестоимость · маржа (область + линии);
2. столбцы «доход / себестоимость / маржа» по неделям, **накопительно**;
3. доли по услугам — **кольцевая** диаграмма; по клиентам — горизонтальные **полосы**;
4. **воронка** «прогоны → результаты → отправлено клиенту» с конверсией на каждой ступени;
5. **тепловая карта** активности: день недели × час (время московское);
6. **спарклайны** внутри KPI-плиток — тренд маржи за 14 дней.

**Срезы (9 измерений):** клиент · услуга · агент · источник · канал доставки · тариф ·
проект · статус клиента · статус прогона.

**Метрики (29).** Как считается каждая:

| Метрика | Формула |
|---|---|
| Доход по подпискам | сумма `price_rub` подписок со статусом active или overdue |
| Себестоимость прогонов | сумма `cost_rub` всех записей в `runs.jsonl` |
| Маржа | доход − себестоимость |
| Маржинальность % | маржа / доход |
| Средний чек (ARPU) | доход / число активных клиентов |
| Прогонов всего | число записей в `runs.jsonl` |
| Успешность прогонов | прогоны со статусом ok / все прогоны |
| Среднее время прогона | среднее по `duration_ms` / 1000 |
| Токенов израсходовано | `usage.totals.tokens.totalTokens` (все токены, включая кэш) |
| Токенов на вход / на выход / из кэша | соответствующие поля логов DSH |
| Расход панели | `usage.totals.rub` — рубли по логам сессий |
| Стоимость одного прогона | себестоимость / число прогонов |
| Результатов готово | число записей в `results.yaml` |
| Отправлено клиенту | результаты со статусом «отправлено» |
| Ожидает отправки | результаты со статусом «ожидает» |
| Доля ручной отправки | не отправленные автоматически / все результаты |
| Клиенты: активные / лиды / на паузе | подсчёт по `status` в `clients.yaml` |
| Подписки: активные / истекают / просрочены | подсчёт по `status`; «истекают» — до конца ≤ 7 дней |
| Долг по счетам | сумма `amount_rub` счетов со статусом issued |
| Конверсия лид → клиент | активные / все клиенты |
| Задач создано / готово / просрочено | реестр задач; просрочено — срок прошёл, задача не закрыта |
| Лотов в источниках · Снимков собрано | суммы по последним снимкам источников |
| Успешность сбора | работающие источники / все источники |

**Топ-5:** услуги по марже · клиенты по доходу · источники по лотам · модели по расходу.

**Честность:** если данных для метрики нет, панель пишет «данных пока нет», а не рисует ноль.
Модель без цены в прайсе помечается «цена неизвестна», и итоговый расход занижен — об этом
сказано рядом. Суммы графиков сходятся с итогами, это проверяет `verify-data.mjs`.

### Меню строится из одного файла — `dashboard/config/nav.yaml`

Каждый пункт меню — независимая запись. Чтобы добавить новый раздел (например новую группу
агентов), допишите запись в нужную группу в `nav.yaml` — логику править не нужно:

~~~yaml
  - id: analytics
    title: "Аналитика"
    items:
      - { id: agents-creative, label: "Агенты-креативы", icon: "spark", counter: failed, counter_kind: bad }
~~~

Поля записи:

| Поле | Что значит |
|---|---|
| `id` | идентификатор раздела и якорь в адресе (`#agents-creative`). **Под этим id должен существовать экран** |
| `label` | название пункта в меню |
| `icon` | иконка: grid, users, card, spark, list, bot, home, chart, ruble, trend, check, plug, box, wallet, bell, pulse, clock, wrench, layers, folder, userplus, lock, gear, book, help |
| `counter` | необязательный счётчик-кружок: `alerts` (тревоги), `overdue` (просроченные подписки), `failed` (упавшие прогоны), `unpaid` (неоплаченные счета) |
| `counter_kind` | `bad` — красный кружок, иначе акцентный |

После правки пересоберите данные: `node marketing-agents/dashboard/collector/collect.mjs`.

Если для раздела нужен **новый экран** (а не существующий), добавьте функцию `VIEWS["<id>"]`
в любой файл `public/app-views*.js` — меню подхватит её автоматически. Готовые экраны:
overview, clients, subscriptions, services, queue, agents, sources, objects, analytics, results,
usage, economy, quality, integrations, payments, notifications, system, journal, infra,
workspaces, projects, team, security, settings, learning, support, account, profile.

Если `nav.yaml` отсутствует или пуст, панель строит меню по встроенной схеме — без меню
она не останется.

**Раздел «Результаты»** (в группе «Аналитика») — это пространство финальных результатов работы:
что сделано, какие файлы получились и **куда это отправлено**. У каждой карточки: заголовок,
краткое описание, период, клиент, услуга и исполнитель, список файлов результата и блок
«Куда отправлено» с каналом (Telegram · VK · WhatsApp · Почта · ссылка), адресом и статусом
(отправлено / ожидает / ошибка / не отправлялось). Поля канала, адреса и статуса **редактируются
прямо в панели** — правка пишется в `registry/results.yaml` атомарно, с копией `.bak-<timestamp>`.
В MVP отправка выполняется **вручную**: панель фиксирует факт, но сама сообщения не рассылает.

**Возможности панели:**

- **свёртывание до иконок** — кнопка ««» в шапке панели; состояние запоминается в браузере
  (для ссылки можно задать `?nav=collapsed` или `?nav=expanded`);
- **счётчики** у пунктов: тревоги на «Обзоре», просроченные подписки, упавшие прогоны, неоплаченные счета;
- **командная палитра** — **Ctrl+K** («перейти к…» и «создать…»);
- **горячие клавиши** — **Alt+1…9** для первых девяти разделов;
- **тема** — тёмная по умолчанию и светлая; кнопка «солнце/луна» есть **в шапке панели** (и в «Профиле»).
  Выбор запоминается; для ссылки можно задать `?theme=light` или `?theme=dark`;
- **вид клиента** — переключатель «Клиент» показывает упрощённую навигацию кабинета заказчика (каркас).

## Управление: тумблеры, группы и что произойдёт

Управление — главная функция панели, поэтому оно вынесено наверх вкладок
**«Агенты»** и **«Источники мониторинга»**.

**Тумблер агента** пишет ровно одно поле `enabled` в `registry/agents.yaml`:
атомарно (temp + rename) и с копией `.bak-<timestamp>`. Рядом с тумблером написано,
что произойдёт: включённый агент получает задачи и запускается по расписанию,
выключенный — нет (уже выданные задачи за ним остаются). Под карточкой видно
**последнее изменение**: дата, время, было → стало и имя файла-копии. Данные берутся
из копий `.bak-*`, поэтому это факт, а не догадка.

**Групповые действия** (одна атомарная правка файла и один бэкап на всю группу):

| Кнопка | Что делает |
|---|---|
| Включить всех / Выключить всех | все агенты (или все источники) разом |
| Только активные | включает агентов со статусом `active`, остальных выключает |
| По группам задач | для каждой группы из реестра — свои «вкл» и «выкл» |
| Только рабочие (источники) | включает источники со статусом `working`/`partial`, остальные выключает |
| По типу источника | http / browser / feed / manual — свои «вкл» и «выкл» |

**Источники.** Выключенный источник **пропускается сбором** — это реализовано в
движке Агента 1 (T18). Включение источника разрешает сбор, но не запускает его само:
сбор запускается отдельно. Уже собранные снимки остаются в статистике независимо от
тумблера.

Проверено: переключение туда-обратно возвращает файл к исходному **SHA-256**, а
групповая правка — тоже (один бэкап на всю группу, комментарии не портятся).

## Доступ по ключу (если открываете панель не только с этого компьютера)

Панель умеет писать в реестр, поэтому снаружи она закрыта ключом:

- **локально** `http://127.0.0.1:8787` открывается **без ключа**, как и раньше;
- **любой другой адрес** требует ключ: `?key=...`, заголовок `X-Dashboard-Key` или
  cookie. Без ключа — `401` и понятная страница «Нужен ключ доступа»;
- ключ создаётся один раз и лежит в `dashboard/config/access.key`, он же печатается
  в консоли при запуске сервера вместе с готовой ссылкой;
- после первого открытия по ссылке с ключом он сохраняется в cookie, и дальше можно
  открывать обычный адрес.

Проверено: снаружи без ключа — 401, с ключом — 200, с неправильным ключом — 401,
локально — 200, тумблер снаружи без ключа — 401.

## Чек-лист приёмки: не забыть DATA_FILES

**Главное правило.** Если сборщик начал писать новый файл в `public/data`, его **обязательно**
нужно добавить в список `DATA_FILES` в `serve.mjs`. Иначе `/api/state` его не отдаст, и фича
**тихо не включится**: панель нарисует старое или пустое состояние без единой ошибки в консоли.

Именно так вышло с `nav.json`: меню из `config/nav.yaml` не доезжало до браузера, панель молча
падала на встроенную схему, и проверка это не поймала, потому что искала текст, который встречался
ещё и в подсказке раздела. Правило появилось из этой ошибки — не повторять.

Чек-лист приёмки любой задачи:

1. `check-dashboard.ps1` — код 0, все разделы из списка на месте.
2. `verify-data.mjs` — «Всё сошлось», включая новые проверки.

## Раздел «Интеграции»: полный каталог

Раздел показывает **весь каталог интеграций** по API: **9 групп, 53 записи**. У каждой записи —
что даёт агенту, направление (читаем / пишем / оба), способ (OAuth, API-ключ, выгрузка файлом),
«где взять доступ» и **статус**: подключено · можно подключить · требует партнёрства ·
нет открытого API. Есть фильтры по группе, статусу и направлению, поиск и счётчики
«подключено N, доступно M».

**Статус «подключено» панель ставит по фактам**, а не по обещаниям: проверяет, установлен ли
пакет в профиле DSH и есть ли он в списке загрузки. Наличие ключа проверяется как факт
(«ключ есть / ключа нет») — **значение ключа не читается и не показывается никогда**.
Где открытого API нет, так и написано, и предлагается выгрузка файлом.

**Как добавить новую интеграцию в каталог.** Каталог — это один файл
`dashboard/config/integrations-full.yaml`. Добавьте запись в нужную группу:

~~~yaml
      - { id: my-crm, name: "Моя CRM", what: "Что даёт агенту",
          direction: both,          # read | write | both
          method: "API-ключ",       # OAuth / API-ключ / выгрузка
          where: "где взять доступ",
          status: available,        # connected | available | partnership | no-api
          package: null,            # id пакета в профиле DSH, если интеграция — плагин
          key_env: MY_CRM_TOKEN }   # имя переменной с ключом (значение не читается)
~~~

Пересоберите данные (`node marketing-agents/dashboard/collector/collect.mjs`) — запись появится
в разделе. Если указать `package`, панель сама пометит интеграцию «подключено», когда пакет
появится в профиле и его списке загрузки.

## Вкладка «Интеграции API» (сводка по профилю)

Состояние «подключено» дашборд определяет **сам, по фактам**, а не по каталогу:

1. читает `package.json` профиля DSH (`C:\Users\<вы>\.dsh\profiles\desktop`) —
   список `dsh.profile.bundles` и `dependencies`;
2. проверяет, что пакет реально лежит в `node_modules` профиля и у него есть загружаемая
   точка входа (`main` / `exports` / `index.js`) или он «пакет-носитель» с патчем
   `dsh.bundle.patch`;
3. сравнивает с `registry/integrations-catalog.yaml`.

Отсюда четыре состояния: **подключено** (в списке загрузки и грузится), **установлено, но
выключено из загрузки** (пакет есть, а в `bundles` его нет), **не загружается** (нет точки
входа) и **не установлено**. Если каталог говорит «подключено», а факты — другое, дашборд
показывает факты и **помечает расхождение**.

**Про секреты.** Дашборд проверяет только **факт наличия** ключа: переменная окружения или
**имя** записи в `~/.dsh/.credentials.yaml`. Значения ключей не читаются и нигде не
показываются — ни в интерфейсе, ни в JSON. Значения ключей не читаются и не показываются нигде — ни в интерфейсе, ни в JSON.

## Вкладка «Источники мониторинга»

- Карточки берутся из `registry/sources.yaml`: имя, статус, тип, авторизация, приоритет,
  последний запуск, ограничения, команда запуска.
- **Тумблер** правит ровно одно поле `enabled` в этом файле: атомарная запись (temp +
  rename) и копия `.bak-<timestamp>`. Проверено: переключение туда-обратно возвращает файл

- **Статистика считается по фактам**: сборщик читает `data/snapshots/*/lots.csv` и

- `data/source-runs.jsonl` — журнал запусков. Если файла нет, вкладка показывает

**Важно:** тумблер источника **разрешает** сбор, но не запускает его. Реально пропускать
источники с `enabled: false` обязаны скрипты сбора — это делает движок Агента 1 (T18).

## Как это устроено

~~~text
  ~/.dsh/sessions/**/session.v4.jsonl.zstd ─┐
  ~/.dsh/storages/session_projcache/*.json ─┼─► collector/collect.mjs ─► public/data/*.json ─► браузер
  marketing-agents/registry/**             ─┘            ▲
                                                          │
                                        serve.mjs (статика + JSON API + тумблер)
~~~

**Важная деталь про логи.** Файл `session.v4.jsonl.zstd` — это **несколько склеенных
zstd-фреймов** (у нас встречалось до 425 на файл). Обычный `zstdDecompressSync()`
возвращает только первый фрейм, поэтому сборщик сам находит все вхождения magic-байтов
`28 B5 2F FD`, режет файл по ним и распаковывает каждый фрейм отдельно, склеивая текст.
Битые фреймы и обрезанные строки не роняют сборщик — они считаются и попадают в
предупреждения.

| Источник | Путь | Что берём |
|---|---|---|

## Тумблер агента: что именно происходит с файлом

Дашборд пишет **только одно поле** — `enabled` в `registry/agents.yaml`:

1. читает файл и находит блок нужного агента по `id`;
2. делает копию `agents.yaml.bak-<timestamp>`;
3. меняет **только строку** `enabled:` внутри этого блока — все комментарии, порядок и
   форматирование остальных строк сохраняются;
4. пишет во временный файл рядом и делает `rename` поверх оригинала (атомарная замена:
   файл никогда не бывает полузаписанным);
5. пересобирает данные и возвращает новое состояние.

Если агент не найден — сервер отвечает 404 и файл не трогает.

Проверено: переключение туда и обратно возвращает файл к исходному SHA-256, то есть
комментарии и форматирование не портятся.

## Как считается расход

- Токены: **вход** (некэшированный), **выход**, **чтение из кэша** — по каждому событию.
- Цены берутся **только** из `registry/prices.yaml` (схема `prices/v1`): ₽ и $ за 1 млн токенов.
  Второго прайса в проекте нет намеренно — два файла с разными числами дали бы разъехавшиеся
  суммы в рублях. `dashboard/config/prices.example.yaml` — просто образец схемы, сборщик его не
  читает. Если сборщик найдёт `dashboard/config/prices.yaml`, он его проигнорирует и напишет
  предупреждение.
- Рубли считаются по ценам в рублях из прайса; доллары — по курсу `rate.usd_rub` из того
  же файла.
- **Модель без цены не выдумывается**: рядом пишется «цена неизвестна». Если в сумму
  входят и такие модели, сумма помечается звёздочкой (`64,75 ₽*`) — это значит
  «неполная, но не выдуманная».
- Если для модели не опубликована цена чтения из кэша, кэш считается по цене входа — это
  **оценка сверху**; сборщик пишет об этом предупреждение.
- Если в прайсе есть блок `peak` (пиковые часы), сборщик сам определяет по времени
  события, попало ли оно в пиковое окно, и считает его с множителем.

## Ограничения (честно)

- Дашборд показывает только то, что есть на этой машине: локальные сессии DSH и реестр.
  Расходы в Яндекс Директе, ВК и на площадках он не знает — их нужно будет добавлять
  отдельным источником.
- События `team/task` в логах **не содержат исполнителя**. Он берётся из
  `dashboard/config/task-owners.yaml` — это ручной снимок общей доски задач. Если доска
  изменилась, обновите файл.
- Расход по агенту реестра считается через `links.yaml`. Пока связь не задана, агент
  показывает нули, хотя его исполнители могли потратить токены.
- Сессии из других рабочих папок (не `marketing-agents`) тоже попадают в общий расход и
  видны как отдельные рабочие пространства на вкладке «Проекты». Это сделано специально:
  иначе общая сумма расхода была бы занижена.
- Задачи из логов DSH — это задачи сборки и эксплуатации команды, поэтому по умолчанию они
  попадают в группу «Сборка системы → Задачи команды».
- Кириллица в путях поддерживается (проверено на `C:\Users\Артем\Desktop\тестDH`), но при
  копировании команд из README следите за кодировкой консоли (UTF-8).
