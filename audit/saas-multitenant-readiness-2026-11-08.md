## 1. Краткое резюме

1. **Продукт технически ближе к SaaS, чем кажется, но платформенного слоя нет вообще.** Движок считает и доставляет отчёты, однако понятия «тенант» в коде не существует: одна панель, один статический ключ, 25 маршрутов, из них 22 пишут на диск, включая файлы **вне проекта** (профиль DSH, роутер моделей, Obsidian). Ключ утёк в лог (`dashboard/logs/server.out.log:9`).
2. **Главный риск запуска подписки — не биллинг, а доверие к цифрам.** На последних боевых данных пересечение ключей лотов 11-04→11-05 = **0**, один оффер дублируется под разными проектами (27 % и 66 % строк), в одном отчёте две медианы одного ЖК, аномалия (12 м², 5,65 млн ₽) подана как «самый дешёвый лот», прогноз печатает −101 190 ₽/м² (`audit/agent1-full-audit-2026-11-08.md:52-56`). Самостоятельная регистрация усиливает этот риск: плохой первый отчёт расходится быстрее хорошего.
3. **Управление заявлено, но не исполняется.** Из 79 полей настроек 35 не читает никто, включая всю группу `schedule/model/priority/alerts/limits`; стоп-кран `limits.stop_switch` не останавливает плановую рассылку, а UI обещает «немедленно запретить любые запуски» (`agent1-full-audit:48-50`).
4. **Метеринг и лимиты фиктивны.** LLM-вызовов 0, «себестоимость факта» = смета прайса 120 ₽ (завышение ~2 порядка против измеренных 0,13–1,27 ₽), `limit_rub`/`limit_tokens` не читает ни один исполняемый модуль — лимит не может сработать.
5. **Платформа не выдержит второго одновременного пользователя.** `execFileSync` в одном потоке: панель мертва 180–300 с, а замер одного прогона — 278,7 с. Уточнение: это замер **недельного** прогона планировщика, где таймаута 180 с нет; вывод «таймаут панели (180 с) убивает реальный сбор» — **гипотеза**, требующая отдельного замера именно панельного пути (`audit/agent1-full-audit-2026-11-08.md:33-34`). Дополнительно: последовательный сбор 20 клиентов ≈ 93 мин; нет очереди, идемпотентности и рабочих ретраев (27 записей журнала на 13 уникальных пар «клиент+дата» — по конвенции Lead: 11 пар с клиентом + 2 discovery с `client: null`).
6. **Есть сильная инженерная база и утверждённый план.** 465 тестов (357 движок + 108 скиллы — статическая оценка; `PA:27` не рекомендует опираться на числа 52/465/319/268), golden-эталон, честные `null` вместо нулей, разведённые ветки 401/403/капча, стенд доставки с перехваченными письмами; архитектура и этапы утверждены 08.11.2026 — новый дизайн не требуется, требуется реализация и закрытие 10 расхождений.
7. **Правовой контур — блокер, а не «потом».** Авито собирается браузером при `robots.txt: Disallow: /`; адреса получателей лежат открыто; оферта и политика — черновики без реквизитов, РКН не подтверждён; при УСН «доходы» кэшбэк не уменьшает налог (`docs/concept-saas-2026-11-04.md:108`, `docs/finance-model-scenarios-2026-11-04.md:73`, `docs/hosting-legal.md:73`). Первый платёж без юрконтура принять нельзя.

## 3. Целевая архитектура MVP (утверждена `PA`; здесь — исполнимая конкретика)

### 3.1 Модель изоляции: **shared + RLS**, не Silo

| Вариант | Решение | Почему |
|---|---|---|
| **Pool/shared (`tenant_id` + RLS FORCE)** | **выбран на MVP** | до ~20 клиентов; одна схема, одна БД, минимум эксплуатации (`PA:202`) |
| Bridge / schema-per-tenant | отложен | уместен на 20–100 клиентов; миграции ×N и пул соединений — не для MVP (`PA:203`) |
| Silo / cluster-per-tenant | отложен | ≥1000 клиентов; избыточно и дорого (`PA:204`) |

Правила: `tenant_id NOT NULL` в каждой таблице с данными тенанта (исключения — глобальные справочники `plans`, `plan_limits`, `processed_webhook_events` и таблицы доступа `users`/`memberships`, где привязка идёт через `memberships.tenant_id`; в приложенном DDL `saas-target-architecture` §2 это так и сделано); `FORCE ROW LEVEL SECURITY` (политика действует и на владельца); `SET LOCAL app.tenant_id` в каждой транзакции (без него политика вернёт 0 строк — это fail-closed); пути объектов `tenant/<tenant_id>/client/<client_id>/…`; секреты — только тенант-скоупные, в secret store, не в общем YAML.

```sql
-- фрагмент; полный DDL на 26 таблиц — audit/saas-target-architecture-2026-11-08.md §2
CREATE TABLE lots (
  id bigserial PRIMARY KEY,
  tenant_id uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  snapshot_id uuid NOT NULL REFERENCES snapshots(id) ON DELETE CASCADE,
  source text NOT NULL, competitor text NOT NULL, project text NOT NULL, lot_id text NOT NULL,
  rooms text, area_m2 numeric(8,2), price_rub bigint, price_per_m2 numeric(12,2),
  finish text, delivery text, promo_flag boolean NOT NULL DEFAULT false, status text, url text,
  UNIQUE (tenant_id, snapshot_id, source, competitor, project, lot_id));  -- tenant_id снимает «схлопывание» lot_id

ALTER TABLE lots ENABLE ROW LEVEL SECURITY;
ALTER TABLE lots FORCE ROW LEVEL SECURITY;
CREATE POLICY lots_tenant_isolation ON lots
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

Тенант = **маркетолог**; иерархия `tenant → client (заказчик маркетолога) → project (ЖК) → ad_account`. `client` — не тенант. Роль `client_viewer` (кабинет клиента маркетолога) отложена, но `client_id` проставляется **сразу** — иначе второй проход по схеме и окно для записей без `tenant_id` (**гипотеза/расхождение** §1 файла `saas-target-architecture-2026-11-08.md:28-31`; в его §8 п.1 речь о другом — об отсутствии SQL в утверждённом пакете).

### 3.2 Биллинг и webhooks

Жизненный цикл (утверждён `PA:409-432`): `registered → trial → active → past_due → frozen → churned`; триал 72 ч от `first_report_at`; `past_due` — grace 7 дней с полным доступом; ретраи D+1/D+3/D+7; `frozen` останавливает прогоны, экспорт и доставку; retention 90 дней; каждый переход — `subscription_events` с CAS по `expected_state`.

- **Провайдер**: `PAYMENT_PROVIDER=mock` сейчас; `yookassa | cloudpayments | robokassa` — после выбора. ККТ/чеки берёт провайдер (обязательство этапа 2). Эквайринг — **2,8 %** (`roadmap-2-sprints.md:41`), учитывается в марже (`finmodel-blueprint.md:671`, `docs/finance-model.md:95`).
- **Идемпотентность**: PK `(provider, event_id)` + `INSERT … ON CONFLICT DO NOTHING RETURNING`; повтор доставки = 200 и no-op. Плюс `UNIQUE (tenant_id, idempotency_key)` в `payments`.
- **Лимиты/overage**: `plan_limits(plan_code, metric, included_qty, warn_pct=80, overage_price_rub, on_limit ∈ warn|pause|killed)`. Проверка **до** создания сущности: 80 % → предупреждение, 100 % → hard-stop, overage — только по явному согласию. Цена превышения и seats-лимиты — «нет данных».
- **Кэшбэк — pass-through, не доход**, отдельно от usage-биллинга; на MVP только зачёт в баланс подписки, вывод деньгами — шаг 2. Предохранитель `Σ accrual ≤ net_return` в `PA` записан как «deferred CHECK» — **в PostgreSQL неисполнимо** (`CHECK` не допускает подзапрос); замена — `CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED` (§2.2 файла `target-arch`).

### 3.3 Как считается стоимость на тенанта

Ключевой факт: **LLM-вызовов нет**, поэтому токенов нет — их нельзя «посчитать»; вводится двухслойный учёт:

1. `usage_events` (пишется всегда, идемпотентный ключ по виду): `(run_id, step_id, provider_request_id)` для LLM, `(run_id, step_id, url_hash)` для страниц, `(run_id, format, template_version)` для отчётов, `(run_id, recipient_hash, template_version)` для доставки, `(tenant_id, agent_id, run_key)` для прогона. Поля `tokens_in/out/cache_read` есть, но при `llm_calls: 0` равны нулю — фиктивных токенов не создаём.
2. `cost_ledger` по слоям **prompt / tool / memory / response / none**: пока LLM нет, `prompt/memory/response = 0`, реальные деньги — в `tool` (Keys.so/SpyWords/Serper) и `none` (единицы работы: страница, строка снимка, отчёт).

Формула цены токенов (для будущего LLM) — из `registry/prices.yaml` (`rub_per_1m_in/out/cache_read`; для `deepseek/deepseek-v4.1-flash` кэш не оценён). Цена «единицы работы» — **нет данных**: измеренные `cost_rub` прогонов 0,13–1,27 ₽ против сметы 120 ₽ (`registry/services.yaml:13`); пока не измерено — в UI «оценка», не «факт».

### 3.4 Обязательные гардрейлы и sandbox на старте

1. **Контракт публикации** (policy-конфиг): единственный источник цифр — снимок; гейт достоверности (пересечение с прошлым снимком ≥ 0,90 — **предложение аудита**, не утверждённый порог; доля ошибок источников ≤ 0,20 — `PA:451`; `min_lots`); запрет публиковать `reliable:false`, прогноз ≤ 0 или вне коридора, лот < 20 м² как «самый дешёвый», пустое значение как 0; у каждой цифры — источник и дата.
2. **Недоверенный ввод**: HTML и тексты акций — только как данные в контейнере, HTML → текст, обрезка (акция ≤ 200 знаков, страница ≤ 8 КБ), детектор инструкций → `injection_suspected`; LLM (когда появится) не имеет прав на инструменты с побочными эффектами.
3. **Валидация выхода**: JSON Schema на аналитику и на выход LLM; провал → `needs_review`, публикации нет.
4. **Tool gateway**: реестр инструментов (name, version, args JSON Schema, side_effects, requires_role, cost_units, egress, idempotency), конверт вызова с `tenant_id/actor/idempotency_key`, RBAC + quota + rate limit, аудит-строка на вызов. Пять инструментов Агента 1 уже описаны схемой (`saas-prompt-gateway-2026-11-08.md` §3.3).
5. **Sandbox**: egress allowlist по доменам источников (+ проверка хоста после редиректа), запись только в namespace тенанта, env-allowlist дочернего процесса, лимиты времени/памяти/страниц; панель перестаёт писать вне проекта (профиль DSH, роутер, vault).
6. **PII и логи**: адреса → `recipient_hash` (sha256 + pepper); redaction секретов (ключ панели, `DSH_SMTP_PASSWORD`, `Authorization`); allowlist получателей **fail-closed**; внешние действия — после подтверждения человеком.

## 5. Чек-лист «готов ли агент к подписке»

### Блокеры (must-have до первого платежа)

1. **Hosted auth + сессии + роли** вместо одного ключа; ключ отозван, в логах не печатается.
2. **`tenant_id` + RLS FORCE + негативный тест изоляции** — сейчас данных чужого арендатора не видит только совесть.
3. **Стоп-кран + лимит + kill-switch, реально читаемые кодом** (`limit_rub`/`limit_tokens` мертвы); очередь вместо `execFileSync`.
4. **Allowlist получателей fail-closed + дедуп отправки `(run_id, recipient)` + подтверждение внешних действий человеком.**
5. **Достоверность цифр:** guard — единственный источник цен, гейт сопоставимости, дедуп оффера, запрет абсурдного прогноза, «нет данных» вместо нуля.
6. **Платёжный провайдер + идемпотентные вебхуки + чеки/ККТ + оферта с автопродлением, политика, 152-ФЗ/РКН** — без этого первый платёж принять нельзя.
7. **Воспроизводимая приёмка:** git, `.gitignore`, единый `CW_PYTHON`, одна команда тестов, статус `partial` вместо `ok`.
8. **Правовой гейт источников:** `sources-legal.yaml`; Авито — только вручную, Домклик — только по договору; ПДн хэшированы, срок хранения зафиксирован.
9. **Анти-абьюз публичной регистрации:** верификация e-mail до первого прогона, капча и rate limit по IP, один триал на e-mail-домен/карту, бюджет прогонов с первого шага (`PA:277-278`, `PA:498`) — иначе бесплатные прогоны при нулевой выручке.

### Желательно (should-have)

- Аудит-трейл действий оператора и журнал доступа; JSON-логи с `run_id`/`tenant_id`, ротация.
- Алерты: стоимость, пустой отчёт, провал источника, рост DLQ, отказ провайдера.
- Tool gateway (реестр + схемы + egress) и sandbox с env-allowlist.
- Единый источник снимков; retention 90 дней; TTL/архивация снимков и артефактов.
- Дедуп и ротация `.bak` (486 файлов / 3,0 МБ); партиционирование `usage_events`.
- Сверка «доход ↔ подписка ↔ счёт» автоматически, а не вручную.

### Можно позже (nice-to-have)

- schema-per-tenant и cluster-per-tenant; мультирегион.
- Векторная память/RAG (Агенту 1 не нужна: любая цифра берётся из структуры).

## 6. Уточняющие вопросы (нужны решения, данных в репозитории нет)

1. **Тарифная сетка.** В проекте три несовместимых: Starter 5 000 / Growth 15 000 / Pro 30 000 (утверждено 08.11, `README.md:59-60`); Lite/Pro/Agency/Enterprise (04.11, `concept-saas-2026-11-04.md:57-60`); `start/business/premium` в реестре (2 900/3 900/5 900/9 900). В задании — `free/basic/pro/usage-based`. **Какую считаем каноном** (и нужен ли free-тариф — в утверждённом плане его нет, вход через триал 3 дня)?
2. **Платёжный шлюз.** Кто берёт на себя ККТ/чеки, рекуррентные списания и СБП: ЮKassa, CloudPayments, Robokassa, Т-Банк? Stripe из задания в каталоге отсутствует — для РФ-платежей, 152-ФЗ и чеков он проблематичен.
3. **LLM в контуре Агента 1 — нужен ли?** Сейчас его нет. Вариант (а): остаёмся детерминированными, делаем policy-конфиг публикации. Вариант (б): добавляем LLM для «Выводов» — тогда промпт, tool gateway, eval и бюджет токенов обязательны (в утверждённом MVP LLM вне объёма).
4. **Кто отвечает за достоверность цифр перед клиентом** — автогейты движка (блокирующие) или ручная проверка оператора? От этого зависит, какие гейты делать жёсткими, а какие — предупреждающими.
5. **Ресурс и горизонт.** 4–8 недель — это этапы 1–2 (доверие + вход/деньги) при 1–2 исполнителях. Один исполнитель + продажи = 20–25 недель до первых платящих (`RM:185` — «21,0 чн при одном исполнителе растягивается»; `RM:53` — соло с продажами 23,0 чн). Сколько часов в неделю выделяется и есть ли второй исполнитель/подрядчик?

**Нет данных (не выдумываем):** бюджет и сроки проекта, компетенции команды, ₽/час, ожидаемый профиль нагрузки и SLA, лимиты SMTP-провайдера, тарифы платных API (Serper/Keys.so/SpyWords), норматив «сколько лотов должен собирать прогон», фактическое срабатывание задачи `Agent1-Weekly`.
