## 3. Пункт 2 task-1: действия «Собрать данные сейчас» и «Сформировать отчёт за неделю»

### 3.1 Причина `spawnSync … EPERM` — установлена

Диагноз: **ограничение среды (песочница DSH), а не неверный путь к интерпретатору**.
Песочница запрещает дочернему процессу piped stdio; `execFileSync` с захватом вывода в трубу
(так работают `runProcess` и `checkProfile`) падает на самом запуске, до старта ребёнка.

Воспроизведение (минимальный зонд, воспроизводит ровно текст из панели):

```
spawnSync C:\Users\Артем\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe EPERM   (code=EPERM, status=null)
spawnSync C:\...\marketing-agents\connectors\ru-marketplace-mcp\.venv\Scripts\python.exe EPERM        (code=EPERM, status=null)
```

При этом оба интерпретатора **на месте**: `Test-Path` = True для node, для python из runtimes DSH и для venv-python проекта.
Значит, версия «панель передала неверный путь» и «неверная рабочая папка» не подтверждается.
Захват вывода через временный файл в той же песочнице работает (`file-stdio: ok` для node и для python),
обычный вывод в консоль (`stdio: inherit`) тоже.

### 3.2 Правка панели

`dashboard\serve.mjs`: helper `execCapture(exe, args, cwd, timeoutMs)` — сначала штатная попытка через трубу
(поведение как было), а если запуск отклонён именно песочницей (`code === 'EPERM' || 'EACCES'` **и** нет `status`,
т. е. процесс не стартовал) — одна повторная попытка с `stdio: ['ignore', fd, fd]` и чтением временного файла.
Повтор безопасен: если процесс не стартовал, побочных эффектов не было (критично для сбора данных и отчёта).
`runProcess` теперь делегирует в `execCapture`, `checkProfile` — тоже. Обход EPERM не «маскируется»:
при реальном ненулевом выходе процесс НЕ перезапускается.

### 3.3 Проверка правки на живом действии

```powershell
Invoke-RestMethod -Uri http://127.0.0.1:8789/api/actions/run -Method Post `
  -ContentType application/json -Body '{"action":"collect"}'
```

Результат: **`ok=True, exitCode=0, durationMs=2881`**, сообщение «Данные пересобраны»,
`result`: sessions=62, tasks=83, rub=3894.65. До правки это же действие возвращало «Не получилось: spawnSync … EPERM»
(зафиксировано Lead'ом на живом прогоне и воспроизведено зондом выше). Действие `collect` — не сухой прогон,
в нём реально запускается дочерний `collector\collect.mjs`, поэтому это сквозное доказательство.

### 3.4 Что осталось по этому пункту (честно)

* Ветка Python у «Сформировать отчёт за неделю» идёт через **тот же** `execCapture`, а режим файла проверен на **том же**
  интерпретаторе venv (`python file-stdio: ok`). Сквозной прогон самого действия я не делал: движок пишет в
  `01-competitor-watch\reports`, а это вне моей зоны записи (`dashboard\**` + этот отчёт).
* После снятия EPERM у отчёта может обнаружиться второй, уже не мой барьер: `serve.mjs` по умолчанию берёт python
  из runtimes DSH (`PYTHON = process.env.DSH_PYTHON || <...>\dependencies\python\python.exe`), а не venv проекта.
  Для живого прогона отчёта стоит поднять панель с `DSH_PYTHON=<marketing-agents\connectors\ru-marketplace-mcp\.venv\Scripts\python.exe>`.

## 4. Must-fix от Lead: честное пустое состояние «Аналитики» по клиентам

### 4.1 Дефект

В `dashboard\public\data\competitor-analytics.json` у клиентов с `exists:false`, `fileName:null`
(файлов аналитики движка нет вообще) причина звучала так:
«Файл аналитики найден, но не разобрался как JSON — данные не показываем, чтобы не выдумывать».
Источник: `collector\lib\competitor-analytics.mjs`, ветка `if (!doc)` не различала «файла нет» и «файл битый».

### 4.2 Правка

Ветка `if (!doc)` теперь различает два случая:

* файла нет (`fileInfo === null`): «Файлы аналитики движка не найдены: в .cache клиента «<id>» нет ни одного
  `analytics-<ГГГГ-ММ-ДД>.json` (проверено `01-competitor-watch\reports\clients\<id>\.cache`). Движок (WP2) ещё не положил результаты — панель не подставляет цифры.»
* файл есть, но битый: «Файл аналитики `<имя>` найден, но не разобрался как JSON …» (с именем файла).

Верхнеуровневая причина (`emptyReason` документа) уже была честной и совпадает по формулировке с `verify-data.mjs`:
«Файлы аналитики движка не найдены: проверено 2 клиент(ов) в `01-competitor-watch\reports\clients\*\.cache` …».
Рендер `public\app-views15.js` правки не требовал — он показывает `emptyReason` как есть.
Заодно убрано дублирующее предупреждение о битом JSON (было два почти одинаковых warning'а на один файл).

Обе ветки проверены отдельным зондом на временной папке (`DASHBOARD_CW_CLIENTS_REPORTS_DIR`):


## 5. Дефект C: расхождение контракта в офлайн e2e-тесте (найден и выровнен)

Первый прогон `test-toggle-e2e.mjs` дал `OK 29, ПРОВАЛ 1`:
`FAIL панель честно сообщает, что блока нет в файле (analyticsPresent=true)`.

Разбор: шаг теста удалял блок `analytics:` из YAML **напрямую, мимо панели**, и ждал, что `/api/state`
сразу покажет `analyticsPresent=false`. Но `/api/state` — это **снимок** собранных данных
(`dashboard\public\data\*.json`), а не живое чтение реестра: он обновляется действиями панели
(`REFRESH_AFTER_WRITE` в `serve.mjs`) и кнопкой «Обновить данные» (`POST /api/collect`, `public\app.js:1225`),
плюс есть явный режим `/api/state?collect=1`. То есть тест требовал то, чего панель и не обещала
(samo поведение панели при этом корректно и честно — теперь это видно по `analyticsPresent=false` после пересборки).

Что сделано: тест перед проверкой честного пустого состояния пересобирает снимок ровно так же, как кнопка
(`POST /api/collect`), а в конце дополнительно проверяет, что снимок вернулся к исходным настройкам
(чтобы прогон теста не оставлял в `public\data` состояние от tmp-копии). Формулировки проверок не ослаблены.

Результат: **`Итог: OK 31, ПРОВАЛ 0`, exit 0**.
