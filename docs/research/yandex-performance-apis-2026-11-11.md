# Яндекс-API для навыков Head of Performance: чего нет в проекте

**Дата:** 2026-11-11 · **Задача:** task-6 · **Область записи:** `marketing-agents/docs/research/**`
**Метод:** только официальная документация Яндекса + GitHub API (метаданные репозиториев). `web_search` в среде
недоступен (HTTP 402), поэтому использовались прямые `web_fetch` по конкретным URL. Всё, что не удалось открыть
напрямую, помечено **«не подтверждено»**.

**Статус у нас (общая база).** В проекте есть только модуль `skills/direct_api` (Direct API v5: `Campaigns.get`,
Reports; Метрика — счётчик, цели, `stat/v1/data`) и регламент скилла `direct-keywords`. Поиск по `marketing-agents/skills`
и `marketing-agents/docs` не находит ни одного упоминания `Units`, `audience:`, `offline_data`, Wordstat API или
`search-api`. Wordstat в артефактах Агента 2 честно стоит «нет данных» (`02-keywords-direct/…`).

**Вывод:** публичного «бесплатного» API Wordstat нет; частотности доступны либо вручную из веб-интерфейса,
либо через платный Yandex Search API (условия не подтверждены из среды). Для наших CSV это означает: пока нет
ключа Search API — честное «нет данных», как сейчас в `02-keywords-direct`.

| Условия доступа (заявка?) | Возможность: OAuth-приложение с правами на сегменты; отдельной процедуры одобрения заявки, как у Direct API, в документации Аудиторий **не описано** | нужен OAuth-app + права |

| Права | `metrika:read` — статистика и чтение счётчиков; `metrika:write` — в т.ч. загрузка любых данных (<https://yandex.ru/dev/metrika/ru/intro/authorization>) | `metrika:read`-сценарий |

| Квоты | 30 запросов/сек с IP; **5000 запросов/сутки на `user_login`** (сброс 00:00 GMT); **`/stat/v1/data` — 200 запросов за 5 минут**; 3 параллельных запроса; при превышении — HTTP 429 (<https://yandex.ru/dev/metrika/ru/intro/quotas>) | нет учёта квот/backoff |
| Особенности | `contains_sensitive_data` (данные с выборкой <10 посетителей скрываются), семплирование (`sampled`, `sample_share`) | не обрабатываем |

**Вывод:** базовое чтение у нас есть, но нет троттлинга под 200/5 мин и обработки семплирования/скрытых данных —
это ближайшее усиление существующего модуля.

## 5. Директ: баллы API (Units)

| Что | Значение / URL | Статус у нас |
| --- | --- | --- |
| Заголовок ответа | `Units: <израсходовано>/<остаток>/<суточный лимит>`, пример `Units: 10/20828/64000`; чей логин списан — в `Units-Used-Login` (<https://yandex.ru/dev/direct/doc/ru/concepts/units>) | **не читаем** (`Units` в коде отсутствует) |
| Суточный лимит | Индивидуальный, зависит от активности кампаний (показы/клики/бюджет), выдаётся сеткой бюджетных порогов; скользящее окно 24 часовых интервалов по 1/24 лимита | — |
| Техническое ограничение | не более **5 одновременных запросов** от одного рекламодателя (там же) | нет ограничителя параллелизма |
| Списание | успех/ошибка вызова и объектов; ошибка вызова — 20 баллов, ошибка операции — 20 баллов, серверные ошибки не списываются | нет — при 429/ошибках слепо повторяем |
| Агентские баллы | `Use-Operator-Units: true` списывает баллы агентства вместо клиента | не используем |
| Правило «остаток <10 % → предупреждать» | В официальной документации **отсутствует** — это наша эксплуатационная политика, не требование Яндекса | предлагается добавить |
| Доступ | Регистрация приложения в Яндекс ID (`direct:api`, при porg — `passport:business`) + заявка на доступ, срок рассмотрения до 7 дней; токен в `Authorization` (<https://yandex.ru/dev/direct/doc/ru/concepts/register>, <https://yandex.ru/dev/direct/doc/ru/concepts/auth-token>, <https://yandex.ru/dev/direct/doc/ru/concepts/access>) | токена нет; проверка `skipped_no_key` |

**Вывод:** нужно парсить `Units` из каждого ответа, ввести порог оповещения (наше правило: warning при остатке
<10 % от суточного лимита), ограничить параллелизм ≤5 и не повторять ошибки, которые списывают баллы.

## 7. Юнит-экономика новостроек (без внешних API)

Рабочий набор формул (фиксируем как внутренний стандарт; привязка к данным — из Метрики/Директа/CRM):

| Метрика | Формула | Что запрашиваем у пользователя |
| --- | --- | --- |
| CPL | расходы канала / число лидов | рекламные расходы по каналам, число заявок/звонков |
| CPQL | расходы / число **квалифицированных** лидов | критерий квалификации лида и число квалифицированных |
| CAC (полный) | (реклама + ФОТ продаж + CRM/сервисы) / число сделок | средняя зарплата отдела продаж, прочие затраты, число сделок |
| CPO / CPA | расходы канала / число броней/сделок | число броней и сделок, окно атрибуции |
| ДРР (ДРР, доля рекламных расходов) | рекламные расходы / выручка от приписанных сделок × 100 % | средняя цена лота, доля приписанных сделок |
| ROMI | (выручка × маржа − расходы) / расходы × 100 % | маржа застройщика/агентства, комиссия |
| Воронка | лид → квал → показ → бронь → сделка (по шагам) | конверсии шагов |
| CAC payback | CAC / (маржа сделки × частота) | срок сделки в новостройке (месяцы), рассрочка/ипотека |
| LTV | маржа сделки × число сделок клиента (с учётом повторных/соседних покупок) | модель повторных обращений |

**Что запрашивать у пользователя (чек-лист):** рекламные расходы по каналам; число лидов и квалифицированных;
число броней и сделок; средний чек и маржа; окно атрибуции/длительность сделки; комиссия агентства;
структура затрат отдела продаж. Без этих входов считаем только CPL/расходы, остальное — «нет данных».

## Что подключить в первую очередь

1. **Баллы `Units` Директа + лимит параллелизма (P0).** Дешевле всего, доступно уже сейчас: парсить заголовок,
   ввести warning при остатке <10 % (наше правило) и потолок 5 одновременных запросов. Причина: без этого любой
   рост запросов упрётся в 429/штрафные баллы и «сожжёт» аккаунт.
2. **Метрика: офлайн-конверсии (P0).** Только так появляется сквозная «реклама → сделка» и CAC/ROMI по факту.
   Нужны: токен с `metrika:offline_data` (или `metrika:write`), счётчик и цель-«JavaScript-событие».
3. **Reporting API — троттлинг и семплирование (P1).** Дёшево доработать существующий `get_metrika_stat`
   (200 запросов/5 мин, 5000/сутки, `sampled`/`contains_sensitive_data`), чтобы отчёты не «врали» молча.
4. **Аудитории API (P1).** Даёт ретаргетинг/look-alike из CRM и сегментов Метрики; права OAuth, заявка не нужна,
   лимиты умеренные (10/мин на изменение сегмента). Нужно уточнить кодовое имя scope в UI приложения.
5. **Wordstat / Yandex Search API (P2, зависит от бюджета).** API существует только как платный сервис Yandex Cloud;
   лимиты/тарифы официально **не подтверждены** из среды. Пока — ручные выгрузки Wordstat как источник, «нет данных» в CSV.
6. **Внешние MCP (P3, только референс).** Из-за лицензионных и security-рисков (`yandex-ads-mcp` без лицензии,
   `N1arko` заморожен) рядом с нашим модулем ничего не ставим; максимум — идеи и сверка покрытия методов.

### Не подтверждено (явно)
- Содержимое и параметры Wordstat API Yandex Cloud (`yandex.cloud/ru/docs/search-api/…` недоступно из среды).
- Кодовое имя scope `audience:write` (в документации есть только словесное описание прав).
- Правило «остаток Units <10 %» в официальной документации отсутствует — это наша политика.
- Формат ручных выгрузок Wordstat — официально не подтверждён.
