## Находки

### E-1 · Critical · venv движка не самодостаточен: базовый интерпретатор лежит внутри рантайма DSH

- **Доказательство:** `connectors/ru-marketplace-mcp/.venv/pyvenv.cfg` → `home = C:\Users\Артем\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python`; `Get-ChildItem .venv\*.dll` — пусто (в корне venv нет `python312.dll`, только `Scripts\python.exe`, `Scripts\pythonw.exe`). Второй `.venv` в проекте отсутствует (поиск по `marketing-agents/**`).
- **Влияние:** venv на Windows берёт стандартную библиотеку и `python3xx.dll` из `home`. Обновление/переустановка DSH, переименование или очистка `.dsh\dsh-runtimes` → **venv перестаёт запускаться**: встают движок Агента 1, недельный прогон (`install\agent1-weekly.cmd:16`) и кнопки панели «сбор»/«отчёт»/«подбор». Штатно восстановить нельзя: pip в venv нет (E-3), uv на PATH нет (E-3), системного Python нет (E-3).
- **Вероятность:** средняя–высокая (любое обновление DSH).
- **Рекомендация:** отдельный venv под проект с фиксацией версий; зафиксировать проверенную процедуру пересоздания (+`wheelhouse` или `uv`); в идеале — переносить venv вне каталога рантайма DSH.
- **Трудоёмкость:** M (2–4 ч).

### E-2 · High · у движка и панели нет декларации зависимостей; PyYAML/openpyxl берутся из venv чужого проекта

- **Доказательство:** в `marketing-agents` нет ни `requirements*.txt`, ни `pyproject.toml` для движка/панели — все найденные манифесты лежат внутри вендоренного коннектора (`connectors/ru-marketplace-mcp/{pyproject.toml,uv.lock,package.json,package-lock.json}` и `packages/*/pyproject.toml`). Пути к интерпретатору: `install/agent1-weekly.cmd:16` → `%MADIR%\connectors\ru-marketplace-mcp\.venv\Scripts\python.exe`; `dashboard/serve.mjs:65-66` → тот же venv. Комментарии-признаки: `01-competitor-watch/scripts/cwlib.py:795` и `:1046` — «PyYAML is NOT part of the DSH runtime»; `cwlib.py:3` — «openpyxl is imported lazily»; `01-competitor-watch/scripts/client_report.py:306-307` — «XLSX не собран (нет openpyxl)».
- **Влияние:** набор пакетов движка определяется **другим проектом**. Обновление коннектора (`uv sync`) может изменить/убрать PyYAML, openpyxl, python-docx — формат отчётов деградирует (честно, но молча: `client_report.py:314-320` пишет проблему, письмо/отчёт уходит без формата). Версии не зафиксированы со стороны движка.
- **Вероятность:** высокая при обновлении коннектора; средняя при пересборке venv.
- **Рекомендация:** завести `requirements-agent1.txt` (PyYAML, openpyxl, python-docx, pytest — с точными версиями) и проверку импортов в гейте.
- **Трудоёмкость:** S (30–60 мин).

### E-3 · High · окружение нельзя пересобрать из проекта: нет pip, нет uv, нет системного Python/py-лаунчера

- **Доказательство:** `.venv\Scripts\python.exe -c "import importlib.util as u;…"` → `pip: False`, `ensurepip: True`, `uv: False`; `Get-Command uv` → пусто; `py -0p` → `'py' is not recognized as an internal or external command`; `where python` → `C:\Users\Артем\AppData\Local\Microsoft\WindowsApps\python.exe`, `python --version` → выход 1 (заглушка Store). - **Влияние:** доустановка хотя бы одного пакета требует ручного `python -m ensurepip` или установки uv; документированная команда на этой машине не выполняется. В сочетании с E-1 это означает: при поломке venv восстановление «по README» невозможно.
- **Вероятность:** высокая при первой же поломке окружения.
- **Рекомендация:** либо включить pip в venv, либо положить `uv`/`wheelhouse` рядом с проектом, либо явно описать bootstrap (`ensurepip`) в `connectors/README.md`.

### E-4 · High · панель запускает РАЗНЫЕ интерпретаторы для разных действий движка; расхождение YAML-парсеров подтверждено

- **Доказательство:** `dashboard/serve.mjs:61` — `PYTHON` = рантайм DSH (**без PyYAML**, п. 9); `:65-66` — `CW_PYTHON` = venv проекта (с PyYAML).
