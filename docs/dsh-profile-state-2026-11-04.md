# Состояние профиля DSH после работ 04.11.2026 (вечер)

Профиль: `desktop`, хост **0.2.1-rc.5**. Записи этого документа касаются только профиля
(`~/.dsh/profiles/desktop`) — рабочая область, боевые снимки и `registry/**` не менялись.

## 1. Установлено из маркета

`@bushizhanghan/dsh-page-monitor` **0.1.2** (в npm есть 0.1.4; профиль закрепил `^0.1.2`).
Команда: `dsh plugin --profile desktop add @bushizhanghan/dsh-page-monitor`.

Что это: слежение за списком страниц — инструменты `page_watch_add`, `page_watch_list`,
`page_watch_check`, `page_watch_remove`, `page_watch_history`, плюс плановый обход
(`intervalMinutes: 60`, `0` — только вручную). Размер 33 КБ распакованным, 6 файлов,
зависимостей нет.

**Что обязательно проверить после перезапуска:** инструментов в текущей сессии нет — набор
инструментов фиксируется при старте окна. Главный риск: страницы он тянет через
`ctx.web.fetch(...)`, а web-провайдера в этом развёртывании, судя по истории со `scrape_webpage`,
нет. Проверка — один вызов `page_watch_check` на заведомо доступной странице
(например, `https://level.ru/projects/southport/`):
* страница скачалась → плагин рабочий, подключаем к сайтам конкурентов из конфига;
* не скачалась → подтверждается отсутствие `ctx.web`, и остаёмся на своём пути чтения
  (анонимный HTTP + Chrome с вынужденным `--no-sandbox`, проверено живьём).

## 2. Побочный эффект установки и его лечение (важно)

pnpm при установке вынес наш собственный плагин `dsh-marketing-skills` в
`node_modules\.ignored` — он не был записан в дерево зависимостей профиля. Из-за этого из
сессии **пропали три скила агента**: `competitor-watch`, `direct-keywords`,
`newbuild-ru-glossary`.

Исправлено: `dsh plugin --profile desktop add file:C:\...\marketing-agents\plugin`
(источник — каталог `marketing-agents/plugin`, `name: dsh-marketing-skills`). Проверено:
запись в `package.json` = `file:C:/Users/Артем/Desktop/тестDH/marketing-agents/plugin`, путь
существует, внутри тот самый плагин; скилы снова видны в каталоге сессии.

Вывод на будущее: перед `dsh plugin add` в этом профиле проверять, что локальные плагины
(`dsh-marketing-skills`, `dsh-locale-ru`, `ru-marketplace-mcp-dsh`) записаны в
`dependencies` — иначе pnpm отправит их в `.ignored`.

## 3. Патч `dsh-scrape-webpage` (применён, ждёт перезагрузки)

Файл: `…\node_modules\dsh-scrape-webpage\lib\fetch.js`, строки 33–35 — проверка формы службы:
`if (typeof shell.run !== 'function') throw new Error('Служба shell не предоставляет run() — …')`.

* резервная копия: `fetch.js.bak-cw-20261104-220951` (откат — вернуть файл из неё);
* `node --check` → exit 0;
* проверено на диске: маркер патча присутствует;
* вызов `scrape_webpage` сразу после патча всё ещё отдаёт старое
  `shell.run is not a function` — запущенный хост держит прежний модуль в памяти;
  ожидаемое поведение появится после перезагрузки плагина/окна;
* патч **не делает инструмент рабочим** — он делает отказ понятным; страницы читает движок Агента 1;
* правка затрётся при обновлении плагина из маркета.

## 4. Предупреждения CLI, замеченные попутно (не наши)

`@deepseek-ai/dsh-subagent-claude-code@0.2.1-rc.3` и `@deepseek-ai/dsh-subagent-codex@0.2.1-rc.3`
объявлены несовместимыми с хостом 0.2.1-rc.5 (их peer-зависимости требуют ровно rc.3).
Профиль оставляет их установленными, но отказывает при старте, пока не выдано исключение
(`dsh plugin allow-version`). Практическое следствие: субагенты Claude Code / Codex в таком
состоянии не запускаются.

## 5. Чек-лист после перезапуска DSH

1. `page_watch_check` на сайте конкурента → вывод о пригодности плагина (пункт 1).
2. Вызов `scrape_webpage` на любом URL → ожидается понятное сообщение вместо сырого `TypeError`.
3. Убедиться, что в каталоге скилов снова есть `competitor-watch`, `direct-keywords`,
   `newbuild-ru-glossary` (после перезапуска они должны загрузиться из восстановленного плагина).
